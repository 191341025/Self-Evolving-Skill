## 1. 认知演进

本文档经历了三轮认知迭代，最终形态与初始设想显著不同。记录演进过程本身是设计的一部分。

### 1.1 第一轮：问题定义（原始假设）

**原始问题**："LLM 可能忘记记录反馈，导致 α/β 不完整。"

**原始目标**：提高反馈覆盖率，降低遗漏。

三个方案被提出：
- A：SKILL.md 新增引用协议（纯指令）
- B：db_query.py 输出增加状态行 + 表名提取（小幅代码）
- C：db_query.py 集成 --cite 自动反馈管线（集成机制）

### 1.2 第二轮：设计原则审视

用 VPRM + 三层表达优先级重新审视：

**方案 C 被排除**：
1. 违反工具独立原则（`computation-layer-design.md` §5.2）
2. 自动化悖论——LLM 记住传 `--cite` ≈ 记住跑 `feedback`
3. SQL 报错 ≠ 知识错误，自动 β+1 有误判风险

**方案 B 被精简**：
- `tables=` 字段删除——LLM 自己写的 SQL，表名是冗余信息
- 只保留 `[QUERY_OK] rows=N` / `[QUERY_FAIL] error=...` 状态行

**方案 A 被缩减**：
- 不新增 SKILL.md 段落（现有 feedback 指令已足够，更多指令 ≠ 更好遵循）
- 仅对现有措辞微调

### 1.3 第三轮：根本性重构（最终认知）

**核心洞察：原始问题定义就是错的。**

"LLM 偶尔忘记反馈"不是系统缺陷——它是系统的正常运行状态。原因：

**1. 衰减模型设计上就是容错的。**

没有反馈时，时间衰减继续工作。知识最终进入 VERIFY → REVALIDATE。α/β 是辅助信号，不是必要信号。公式 `C(t) = C0 × e^(-λ_eff × t)` 中，即使 λ_eff = λ_base（无反馈，α=β=0），衰减仍然正常运行。

**2. 强制反馈有确认偏差风险。**

如果 LLM 机械性地在每次 SQL 执行后 α+1，置信度会被虚高。`bayesian-feedback-design.md` §10 专门警告了这个风险——"任务完成不等于知识正确"。强制反馈把"SQL 跑通了"等价于"知识被验证了"，这恰恰是确认偏差的来源。

**3. 自然反馈信号质量更高。**

类比：食堂里同事偶然聊到"最近某道菜做得不错"——他开口说，意味着这个信号**强到越过了"不值得说"的阈值**。这比每天强制填满意度表的信息量大得多。

LLM 在使用知识时，如果真正意识到"这条 schema 帮我避免了一个错误连表"而主动记录 feedback success，这一次 α+1 的信息量远大于 50 次机械性的"SQL 跑完了所以 α+1"。

**4. LLM 本质在模仿人类思维。**

人类不会每次使用知识后都做记录。人类是在**有感触**时才做反馈——"这个好用""这个有坑"。顺应 LLM 模仿人类思维的特点，而非对抗它，才能得到更真实的反馈信号。

**5. 反馈的价值来自跨会话聚合，而非单次完整性。**

每一次 Claude Code 会话就是一个"食客"——共享同一份 SKILL.md 和 references/。食堂里 100 个人各自不定时说"某菜不错"或"某菜太咸"，聚合起来就是真实的质量画像。没有任何一个人需要每天完整评价所有菜品。

贝叶斯 α/β 模型天然为此设计：每次 feedback 是一个独立观察事件；不需要每次都观察；观察越多，(β+1)/(α+1) 越接近知识的真实质量。这是大数定律在知识管理中的应用。

当前架构是模型无关的（references/ 是纯 markdown，decay_engine 是独立 CLI）。如果未来多个 LLM 实例共享同一 knowledge base，α/β 自然聚合来自不同"食客"的反馈，无需改动任何代码。

## 2. 最终方案

### 2.1 定位重构

| | 原定位 | 最终定位 |
|--|--------|---------|
| 标题 | 硬反馈自动化 | 反馈机制优化 |
| 目标 | 提高反馈覆盖率 | 提高反馈**信号质量** |
| 策略 | 让 LLM 更频繁地反馈 | 让自然发生的反馈更容易、更准确 |
| 对遗漏的态度 | 缺陷，需要修复 | 正常，系统容错 |

### 2.2 实施内容

**仅做一件事：db_query.py 输出增加确定性状态行。**

这不是为了"提醒 LLM 去反馈"，而是为了**当 LLM 自然决定反馈时，能更容易地判断 success/failure**。

变更：

```
正常查询结束后追加：
[QUERY_OK] rows=<N>

异常查询后追加：
[QUERY_FAIL] error=<errno> message=<msg>

无结果时：
[QUERY_OK] rows=0
```

不做 tables 提取（LLM 写的 SQL，表名它自己知道）。
不做 SKILL.md 指令新增（现有指令已足够清晰）。

### 2.3 SKILL.md 现有指令评估

当前 SKILL.md 的 feedback 指令：

```
Gate 4 — FRESHNESS (feedback): After operations using knowledge
  Hard signals (weight=1.0, default):
    → SQL execution success/failure involving known columns/tables
    ...
  No clear outcome → do NOT record feedback
```

**评估**：已经是合理的结构化 NL。关键是 `No clear outcome → do NOT record feedback` 这行——它允许不反馈。无需修改。

## 3. 锁定的决策

| # | 决策项 | 结论 | 理由 |
|---|--------|------|------|
| D1 | 总体方案 | **仅 B（精简版）** | A（指令强化）不必要——现有指令够用；不追求反馈频率 |
| D2 | tables 提取 | **不提取** | 冗余信息，LLM 写的 SQL 自己知道表名 |
| D3 | 反馈时机 | **自然发生即可** | 不强制即时也不强制批量，LLM 有感触时反馈 |
| D4 | fetch_structure.py | **不改** | 输出天然清晰，无需增强 |
| D5 | SKILL.md | **不改** | 现有 feedback 指令已足够 |

### 代码改动范围

| 文件 | 变更 | 行数 |
|------|------|------|
| `db_query.py` | 正常/异常结束时各追加一行状态输出 | ~5 行 |
| `tests/test_db_query.py` | 状态行输出断言 | 新建或追加 |

**总改动量：极小。** 这是正确的——一个已经工作良好的反馈机制不需要大改。

## 4. 设计原则回溯

| 原则 | 在本文档中的体现 |
|------|-----------------|
| **VPRM** | 状态行是规则提供的确定性信号（QUERY_OK/FAIL），LLM 负责判断"是否要反馈"和"反馈哪条" |
| **三层优先级** | 状态行 = 结构化输出（比自由文本更明确）；不上升到公式层（无数学精确度需求）；不为了结构化而结构化（只加最小必要标记） |
| **自然反馈 > 强制反馈** | 不增加 SKILL.md 指令压力；允许遗漏；信任衰减模型的容错能力 |

## 附录：方案 C 的完整否决记录

保留于此供设计回溯参考。

方案 C（集成管线 --cite 自动反馈）被否决，三个结构性理由：

1. **违反工具独立原则**：`computation-layer-design.md` §5.2 约定工具间不直接调用。C 方案让 db_query 调用 decay_engine，破坏架构约束。
2. **自动化悖论**：LLM 记住传 `--cite` 和记住跑 `feedback` 的认知负担等价。核心遗漏问题未真正解决。
3. **误判风险**：SQL 报错 ≠ 知识错误（可能是 SQL 语法问题）。自动触发 β+1 会污染反馈数据。
4. **（第三轮补充）哲学层面**：方案 C 追求"每次 SQL 都产生反馈"——这本身就是错误目标。强制的 100% 覆盖不如自然的高质量信号。
