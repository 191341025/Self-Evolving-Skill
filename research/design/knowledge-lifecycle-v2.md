## 1. 设计背景

### 1.1 项目重定位

**旧定位**：Self-Evolving Skill 是一个数据库调查技能，通过使用积累数据库领域知识。

**新定位**：Self-Evolving Skill 是一个**知识生命周期治理机制**。五道门协议、置信度衰减模型、选择性注入等核心组件与领域无关。数据库调查是第一个应用场景，但不是唯一场景。

核心认知转变：
- 价值不是"缓存查询结果"，而是"积累业务理解"
- 知识来源不限于数据库查询，整个 Claude Code 工作流中的业务讨论、架构决策、问题排查都会产生有价值的知识碎片
- 类比：老 DBA vs 新人的差距不在于谁能查库，而在于业务认知的积累

### 1.2 现有单阶段模型的局限

当前设计是**单阶段**：知识通过五道门 → 写入 → 衰减。

问题在于：
- **五道门是一次性判断**：LLM 在写入那一刻认为有价值就入库了。如果判断失误，低价值知识获得永久居留权
- **缺少"证明期"**：真正有价值的知识应该在多次使用中证明自己，而非一次通过就定性
- **存储规模限制**：MD 文件 + 路由表适合几十条知识，但通用化后知识量级可能达到数百条，需要语义检索能力

### 1.3 新模型的核心洞察

**知识应该经历两个阶段，就像学术论文要经过同行评审才能正式发表：**

1. **准入阶段（Distillation）**：一条知识不是一次判定就入库，而是需要多次使用/确认的累计证据才能晋升。越近的确认、越可靠来源的确认、越核心场景的确认，权重越高。
2. **保鲜阶段（Freshness）**：已晋升的知识随时间自然衰减，通过使用反馈调节衰减速度。错误比正确更值得警惕——一次用错大幅扣分，一次用对只加一点点。

## 2. 两阶段知识生命周期

### 2.1 全景视图

```
知识碎片产生（工作过程中）
    │
    ▼
  Gate 1 VALUE：值得跟踪吗？
    │ 是
    ▼
  Gate 2 ALIGNMENT + Gate 3 REDUNDANCY（向量相似度辅助）
    │ 通过
    ▼
┌─────────────────────────────────────────────┐
│  阶段一：知识准入（CANDIDATE）                 │
│                                              │
│  distill_score = Σ (Wc × Wr × e^(-λd × d))  │
│                                              │
│  每次被使用/确认 → 累加一项                     │
│  长期无确认 → 旧项自然衰减                      │
│  distill_score < 下限 → 淘汰                   │
│  distill_score ≥ 阈值 → 晋升 VALIDATED         │
└────────────────────┬────────────────────────┘
                     │ 晋升
                     ▼
┌─────────────────────────────────────────────┐
│  阶段二：知识保鲜（VALIDATED）                  │
│                                              │
│  C(t) = C0 × e^(-λ_base × (β+1)/(α+1) × t) │
│                                              │
│  使用成功 → α += 0.3（严谨加分）               │
│  使用失败 → β += 1.5（激进扣分）               │
│                                              │
│  C ≥ 0.8 → TRUST    直接使用                  │
│  C ≥ 0.5 → VERIFY   使用但标注需验证            │
│  C < 0.5 → REVALIDATE  先验证再使用            │
└─────────────────────────────────────────────┘
```

### 2.2 阶段一：知识准入（Knowledge Distillation）

#### 公式

```
distill_score(t) = Σ_i [ Wc_i × Wr_i × e^(-λd × (t - t_i)) ]
```

- **i**：第 i 次确认事件
- **t_i**：第 i 次确认发生的时间
- **t**：当前时间
- **Wc_i**：该次确认的来源可信度权重（Credibility）
- **Wr_i**：该次确认的场景相关性权重（Relevance）
- **λd**：准入阶段的时间衰减系数（暂定 0.01，半衰期 ≈ 69 天）

#### Wc — 确认来源可信度（Credibility Weight）

核心依据：确认来源越确定，信号质量越高（VPRM 原则的延伸）。

| 确认来源 | Wc 参考值 | 示例 |
|---------|----------|------|
| 工具/规则硬验证 | 1.0 | SQL 执行成功验证了表关系、API 返回确认了字段含义 |
| 用户显式确认 | 0.8 | 用户说"对，这个业务规则是这样的" |
| LLM 语义判断 | 0.6 | LLM 在使用知识时判断"这和当前观察一致" |
| 间接推测 | 0.3 | 知识被提到但未被直接验证 |

#### Wr — 确认场景相关性（Relevance Weight）

核心依据：知识在越核心的位置被验证，验证越深入。

| 使用场景 | Wr 参考值 | 示例 |
|---------|----------|------|
| 核心依据：知识是完成任务的关键 | 1.0 | 依赖该表关系知识才能写出正确的 JOIN |
| 辅助参考：知识辅助了决策 | 0.5 | 知道该字段含义帮助理解了查询结果 |
| 边缘提及：知识被触及但未实质使用 | 0.2 | 在浏览 schema 时看到了该知识涉及的表 |

#### Wc 和 Wr 的关系

两个权重独立正交：
- Wc 回答"谁说的"（信号来源可靠性）
- Wr 回答"在什么场景下说的"（信号场景深度）

乘积 Wc × Wr 表达"一次确认的综合质量"：
- 最高质量（1.0 × 1.0 = 1.0）：工具硬验证 + 核心依据场景
- 最低质量（0.3 × 0.2 = 0.06）：间接推测 + 边缘提及

#### 晋升与淘汰

- **晋升阈值**（暂定 `T_promote = 2.0`）：`distill_score ≥ T_promote` → 状态从 CANDIDATE 晋升为 VALIDATED
  - 含义：约需 2-3 次高质量确认，或更多次中低质量确认
  - 例：3 次工具核心验证（≈ 1.0 + 0.95 + 0.90 = 2.85）→ 晋升
  - 例：5 次 LLM 辅助参考（≈ 0.3 × 5 项，含衰减 ≈ 1.35）→ 未达阈值，继续积累
- **淘汰下限**（暂定 `T_expire = 0.1`）：`distill_score < T_expire` → 从 CANDIDATE 中移除
  - 含义：长期无人使用的候选知识自然消亡

**所有阈值均为初始参考值，以实际业务验证结果为准。**

#### 公式性质

1. **近期偏好**：近期确认权重更高，远期确认自然衰减
2. **质量敏感**：高质量确认（Wc × Wr 高）远比低质量确认有效
3. **累积但有界**：旧确认持续衰减，不会无限增长
4. **自然淘汰**：无新确认的候选知识 distill_score 持续下降，最终被淘汰
5. **抗噪声**：单次低质量确认（Wc × Wr = 0.06）几乎无法推动晋升

### 2.3 阶段二：知识保鲜（Knowledge Freshness）

#### 公式（沿用现有设计）

```
C(t) = C0 × e^(-λ_base × (β+1)/(α+1) × t)
```

- **C0**：初始置信度（晋升时 = 1.0，invalidate 后 = 0.1）
- **λ_base**：按知识类型不同（schema=0.003 ... data_snapshot=0.050）
- **(β+1)/(α+1)**：贝叶斯因子
- **t**：距上次确认的天数

#### 不对称反馈——核心设计哲学

**"正确持严谨态度，错误持激进态度。"**

| 事件 | 操作 | 权重 | 数学效应 |
|------|------|------|---------|
| 使用成功 | α += success_w | 0.3 | 衰减减缓约 23%（单次） |
| 使用失败 | β += error_w | 1.5 | 衰减加速约 150%（单次） |

不对称比 = 1:5（error_w / success_w = 1.5 / 0.3 = 5）

含义：**需要约 5 次成功才能抵消 1 次失败的影响。** 这是刻意的——一次用对可能是巧合，一次用错强烈暗示知识本身有问题。

#### 数值验算

| 场景 | α | β | 贝叶斯因子 (β+1)/(α+1) | 衰减速度变化 |
|------|---|---|----------------------|------------|
| 初始状态 | 0 | 0 | 1.0 | 基准 |
| 1 次成功 | 0.3 | 0 | 0.77 | 减缓 23% |
| 1 次失败 | 0 | 1.5 | 2.50 | 加速 150% |
| 1 成功 + 1 失败 | 0.3 | 1.5 | 1.92 | 净加速 92% |
| 5 成功 + 1 失败 | 1.5 | 1.5 | 1.00 | 回归基准 |
| 3 成功 + 0 失败 | 0.9 | 0 | 0.53 | 减缓 47% |

#### 置信度分级（沿用现有设计）

| 范围 | 级别 | 行为 |
|------|------|------|
| C ≥ 0.8 | TRUST | 直接使用，不需验证 |
| 0.5 ≤ C < 0.8 | VERIFY | 使用但标注"此知识待验证" |
| C < 0.5 | REVALIDATE | 必须先通过工具验证才能使用 |

### 2.4 两阶段衔接

```
CANDIDATE ──(distill_score ≥ T_promote)──> VALIDATED (C0=1.0, α=0, β=0)
                                               │
                                               ├── 使用成功 → α += 0.3
                                               ├── 使用失败 → β += 1.5
                                               ├── 人工废止 → C0 = 0.1, α=0, β=0
                                               └── 重验证通过 → C0 = 1.0, α=0, β=0
```

晋升时：
- 状态标记从 CANDIDATE 改为 VALIDATED
- C0 设为 1.0（完全可信）
- α, β 归零（开始新的反馈周期）
- confirmed_at 设为晋升日期
- 保留原始 distill_score 历史（可追溯晋升依据）

## 3. 五道门协议在两阶段中的映射

### 3.1 映射总览

| 门 | 原始职责 | 阶段一（CANDIDATE） | 阶段二（VALIDATED） |
|----|---------|-------------------|-------------------|
| Gate 1 VALUE | 知识是否有复用价值 | **入口门**：决定是否成为 CANDIDATE | 不再参与（已通过准入证明价值） |
| Gate 2 ALIGNMENT | 是否与已有知识矛盾 | 检查与 VALIDATED 知识的矛盾（向量相似度辅助） | 使用中发现矛盾 → 触发修正 |
| Gate 3 REDUNDANCY | 是否与已有知识重复 | 检查 CANDIDATE + VALIDATED 中的重复（向量相似度辅助）；重复则合并 distill_score | 不再参与 |
| Gate 4 FRESHNESS | 衰减元数据管理 | **拆分为 Phase 1**：distill_score 累积与晋升 | **拆分为 Phase 2**：C(t) 衰减与反馈 |
| Gate 5 PLACEMENT | 存放位置 | 写入向量数据库 CANDIDATE 分区，附带 metadata | 晋升时迁移到 VALIDATED 分区 |

### 3.2 Gate 2 ALIGNMENT 的增强

向量数据库使 Gate 2 的矛盾检测更精确：

- **现有方式**：依赖 entities 标签做精确匹配 → search 命令 → LLM 比对
- **增强方式**：向量相似度找到语义相近的条目 → LLM 判断是否矛盾

例：候选知识"orders 表的 status=1 表示已完成"，向量检索找到已有知识"orders.status 字段：0=待处理, 1=进行中, 2=已完成" → 矛盾，触发修正流程。

### 3.3 Gate 3 REDUNDANCY 的增强

向量相似度天然适合去重：

- **现有方式**：entities 精确匹配 + LLM 语义判断
- **增强方式**：向量相似度 > 阈值 → 大概率是同一条知识的不同表述 → LLM 确认后合并

合并策略：将新确认的 Wc × Wr 贡献累加到已有条目的 distill_score 上，而非创建新条目。

## 4. 知识来源与触发机制

### 4.1 知识来源分类

在 Claude Code 工作流中，以下场景会产生有治理价值的知识：

| 知识类型 | 来源场景 | 示例 |
|---------|---------|------|
| 结构性知识 | 数据库查询、代码阅读 | 表关系、API 接口结构、模块依赖 |
| 业务规则 | 需求讨论、问题排查 | "退款必须在 7 天内"、"该字段为空时走默认逻辑" |
| 项目约定 | 团队协作、代码审查 | 命名规范、架构决策、部署流程 |
| 数据特征 | 数据分析、性能排查 | 表数据量级、热点数据分布、索引使用情况 |
| 工具经验 | 工具使用、调试 | 特定 API 的坑、有效的参数组合、常见报错原因 |
| 调试模式 | 问题排查 | "这类错误通常是因为..."、"排查顺序应该是..." |

### 4.2 激活模式

**模式 A：宽触发 Skill（主模式 — 知识检索端）**

SKILL.md 的 frontmatter trigger 覆盖大部分工作场景。当 Skill 激活时：
- 检索向量数据库中与当前任务相关的 VALIDATED 知识
- 按 Knowledge-First 策略使用知识（TRUST 直接用 / VERIFY 标注 / REVALIDATE 先验证）
- 使用后自然产生反馈信号（Phase 2 的 α/β）

**模式 B：会话收割（补充模式 — 知识写入端）**

通过 `/harvest` 命令（或类似机制）在会话结束前触发知识提取：
- 回顾本次会话的关键交互
- 提取候选知识碎片
- 每条碎片过 Gate 1 → Gate 2 → Gate 3 → 写入 CANDIDATE 分区

**两种模式的分工**：
- 模式 A 负责**读**：检索知识、使用知识、产生反馈
- 模式 B 负责**写**：提取知识、准入判定、写入候选

这种分工使知识写入不干扰正常工作流，同时保证知识检索随时可用。

## 5. 存储架构

### 5.1 从 MD 到向量数据库的演进动机

| 维度 | MD 文件方案 | 向量数据库方案 |
|------|-----------|-------------|
| 检索方式 | entities 精确匹配 | 语义相似度检索 |
| 去重能力 | 依赖 LLM 判断 | 向量距离 + LLM 确认 |
| 规模上限 | ~100 条（路由表 + 文件拆分管理） | 数千条（向量索引自动管理） |
| 人可读性 | 高（直接读 MD） | 需要工具辅助查看 |
| Git 追踪 | 天然支持 | 需要额外策略（如定期导出快照） |
| 两阶段支持 | 需要额外标记系统 | 天然支持分区/标签 |

**决策**：向量数据库。知识通用化后的规模需求、语义检索需求、两阶段分区需求，三者合力使 MD 文件方案不再适用。

### 5.2 存储结构设计

```
向量数据库
├── CANDIDATE 分区
│   ├── content（知识文本）
│   ├── embedding（语义向量）
│   └── metadata
│       ├── type（知识类型：schema / business_rule / ...）
│       ├── status = "CANDIDATE"
│       ├── created_at（首次发现时间）
│       ├── distill_history（确认记录列表）
│       │   └── [{t, Wc, Wr, context_summary}, ...]
│       ├── distill_score（当前得分，可实时计算或缓存）
│       └── source_domain（来源领域：db / code / business / ...）
│
└── VALIDATED 分区
    ├── content（知识文本）
    ├── embedding（语义向量）
    └── metadata
        ├── type（知识类型）
        ├── status = "VALIDATED"
        ├── promoted_at（晋升时间）
        ├── confirmed_at（最后确认时间）
        ├── C0, alpha, beta（衰减参数）
        ├── lambda_base（按 type 确定）
        ├── feedback_history（反馈记录列表）
        └── source_domain
```

### 5.3 技术选型（待评估）

| 方案 | 特点 | 适用性评估 |
|------|------|-----------|
| **ChromaDB** | Python 原生、本地文件存储、API 简洁 | 最轻量，适合单用户本地场景 |
| **LanceDB** | 基于 Lance 列存格式、零依赖嵌入 | 性能好，但生态较新 |
| **sqlite-vec** | SQLite 扩展、与现有 SQLite 路线一致 | 如果想保持"单文件可携带"的特性 |

**选型标准**：本地运行、无需服务进程、Python 集成、文件可随项目目录携带。

**选型决策留到原型阶段**，先完成设计对齐。

### 6.3 db-investigator 的定位

db-investigator 从"技能本身"变为"第一个领域插件"：

```
知识治理层（通用）                领域插件层（专用）
─────────────────             ──────────────
decay 公式 + 模型               db_query.py
五道门协议                      fetch_structure.py
向量数据库读写                   fetch_index.py
distill_score 计算              db_config.ini
/harvest 知识收割                数据库调查指令
```

治理层可被任何领域复用。领域插件提供特定领域的工具和触发条件。

## 7. 开放问题与待验证项

以下问题需要在原型实现和实际使用中验证：

| # | 问题 | 初始假设 | 验证方式 |
|---|------|---------|---------|
| 1 | Phase 1 晋升阈值 T_promote 应该是多少？ | 2.0 | 观察前 20-30 个 CANDIDATE 的 distill_score 分布 |
| 2 | Phase 1 淘汰下限 T_expire 应该是多少？ | 0.1 | 观察长期未确认的 CANDIDATE 的 score 变化 |
| 3 | Phase 1 衰减系数 λd = 0.01 是否合适？ | 半衰期 69 天 | 观察知识的实际有效周期 |
| 4 | Wc/Wr 的参考值是否需要调整？ | 见 2.2 节 | 观察不同来源确认的实际区分度 |
| 5 | 不对称比 5:1 是否合适？ | error_w=1.5, success_w=0.3 | 观察 1 次失败后的恢复路径是否合理 |
| 6 | 向量数据库选型 | ChromaDB（最轻量） | 原型实现后评估性能和体验 |
