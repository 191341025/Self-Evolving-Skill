## 本次讨论的核心结论

### 结论 1：项目本质重定义

**旧定位**：数据库调查技能 + 知识管理
**新定位**：工作过程中碎片化业务知识的治理机制，数据库调查是第一个应用场景

关键认知：
- 价值不是"缓存数据库查询结果"，而是"积累业务理解"
- 类比：熟悉数据库的老 DBA vs 新人——差距不在于谁能查库，而在于业务认知的积累
- 任何 Skill 在做任何工作时都可能产生值得治理的业务知识碎片，不限于数据库场景

### 结论 2：路 B — 碎片写入 + 读取时组装

讨论中对比了两条路：
- **路 A（否决）**：写入时提炼完整业务总结 → 存储 → 直接读取
  - 问题：触发时机不可判定、粒度过粗导致衰减失效、复用灵活性低
- **路 B（采纳）**：逐查询捕获原子事实碎片 → 读取时 LLM 从多个 TRUST 碎片组装业务回答
  - 优势：不需要新机制（现有 Post-Investigation Checkpoint 已能捕获碎片）、每条碎片独立衰减、同一组碎片能回答多种问题
  - LLM 天然擅长从碎片组装连贯叙述——这正是语义综合能力

### 结论 3：Knowledge-First Response Strategy

当用户提问且存在相关已积累知识时：

```
Case 1: TRUST 碎片完整覆盖问题
  → 直接从碎片组装回答，不查库
  → 标注来源和最后确认日期

Case 2: TRUST 碎片部分覆盖 / 有 VERIFY 碎片
  → 已知部分直接回答，缺失或 VERIFY 部分做针对性查询

Case 3: 无相关知识 / 全是 REVALIDATE
  → 完整调查流程（当前行为）
```

核心判定分工（符合 VPRM）：
- "置信度够不够" → 代码算（decay_engine.py）
- "碎片是否覆盖问题" → LLM 语义判断

### 结论 4：架构分离

```
治理层（通用，与领域无关）         领域技能层（专用）
───────────────────           ──────────────
decay_engine.py               db_query.py
core/formulas.py              fetch_structure.py
core/models.py                fetch_index.py
core/parser.py                db_config.ini
五道门协议                     数据库调查指令
置信度衰减模型                  references/ 中的数据库知识
```

治理层代码当前已和数据库逻辑解耦（现有代码几乎不用改），需要的是：
- 拆分 SKILL.md（治理协议 vs 数据库指令）
- 调整目录结构（knowledge-governance/ vs db-investigator/）

### 结论 5：Skill 身份，保留 Agent 路径

当前设计的行为是"响应式"（有工作产出 → 触发治理），不需要自主循环，Skill 足够。
当出现需要自主性的场景（如定期扫描衰减状态、主动提醒验证）时再升级为 Agent。
存储演进路径不变：文件 → SQLite → 向量数据库。
