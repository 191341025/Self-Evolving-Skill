# 探索-记忆-治理：未展开的思考草稿

> 状态：原始想法，待逐条验证和细化

---

## 背景

与王军杰交流中已输出的内容：
1. 记忆内容能否用标准评判后称作"问题"
2. 问题随探索结果衰减或强化
3. 自动提炼的问题与用户反馈的问题做价值对标
4. 已解决的问题也能产生反馈，甚至以"经验"身份重新参与探索
5. 探索结果应自然反馈而非强制反馈
6. 已解决的问题受时间因子影响，可能过期后重新以"问题"身份跟着 agent 出去
7. 系统因此表现出"忙碌-沉默"的呼吸节奏

以下是**未输出的、需要进一步验证的延伸想法**。

---

## 核心命题

在探索（Exploration）与记忆（Memory）之间，需要一个**治理层**——对复杂的反馈信息做流水线化的分工处理，让记忆保持记忆、探索始终待命，在迭代中持续提升质量。

---

## 待验证的想法清单

### 想法 1：反馈信号的多源汇聚

反馈不只来自一个地方，至少有三个源头：

| 源头 | 性质 | 信号特征 |
|------|------|---------|
| 用户反馈 | 人类判断 | 高信号质量，低频率，不可预测 |
| LLM/Agent 反馈 | 模型自我评估 | 中信号质量，可批量，有确认偏差风险 |
| 工具/规则反馈 | 确定性结果 | 最高信号质量，自动产生，覆盖面有限 |

**待验证**：三种信号是否需要不同的权重？是否需要不同的处理管道？

### 想法 2：问题的生命周期

问题不是静态的。一个问题从诞生到消亡可能经历：

```
从记忆中提炼出异常/矛盾 → 形成"问题"
  → 等待探索机会（待命）
  → 跟随 agent 出去探索
  → 探索成功 → 问题变为"经验"，带着答案回到记忆
  → 时间推移 → 经验衰减 → 重新变为"问题"
  → 下一轮探索
```

**待验证**：这个生命周期是否需要形式化？问题和经验是否需要不同的 decay 参数？

### 想法 3：流水线化的环节分工

复杂反馈不应该由一个模块处理。可能的分工：

```
信号采集（工具层）→ 信号分类（规则层）→ 价值判定（LLM 层）→ 写入/更新（工具层）
```

每个环节做自己最擅长的事：
- 工具层：采集确定性信号、执行写入
- 规则层：分类信号来源、计算衰减、阈值判定
- LLM 层：语义价值判断、矛盾检测、冗余判断

**这就是 VPRM 原则在反馈处理中的应用。**

**待验证**：这个流水线是否过度设计？哪些环节真正需要分离？

### 想法 4：记忆与探索的分工边界

| | 记忆（Memory）的职责 | 探索（Exploration）的职责 |
|--|-------------------|----------------------|
| 做什么 | 存储、检索、衰减管理 | 发现新知识、验证过期知识 |
| 不做什么 | 不主动寻找问题 | 不长期存储 |
| 输入 | 探索带回的成果、用户反馈 | 记忆中提炼的问题 |
| 输出 | 给探索提供问题种子 | 给记忆提供新鲜内容 |

**待验证**：这个分工是否清晰？边界情况如何处理？

### 想法 5：呼吸节奏的自适应

系统的忙碌/沉默节奏不应该是固定的，应该自适应：

- 大量知识同时过期 → 集中探索期（忙碌）
- 新领域刚开始 → 高频探索期（忙碌）
- 知识库稳定 → 低频验证期（沉默）
- 业务突变 → 紧急探索期（忙碌）

**待验证**：节奏由什么控制？是触发信号的密度自然决定，还是需要显式的调度机制？

## 与现有系统的关系

这些想法如果成立，它们和我们现有的 Self-Evolving Skill 的关系是**延伸而非替代**：

- 五道门 = 治理层的具体实现（已有）
- α/β + 衰减 = 信号质量管理的数学基础（已有）
- 自然反馈原则 = 反馈哲学（已确认）
- 问题提炼 + 定向探索 = 新方向（未实现，当前系统是 demand-driven）

**当前不需要改变任何现有设计。** 这些想法是更远期的方向思考。
